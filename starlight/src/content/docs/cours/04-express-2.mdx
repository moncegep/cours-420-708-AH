Certaines responsabilités reviennent dans de nombreuses requêtes sans appartenir directement au domaine de l'application :

- journaliser les requêtes;
- lire un corps JSON;
- vérifier l'identité de l'utilisateur;
- contrôler ses droits;
- valider les données reçues;
- charger une ressource demandée.

On pourrait effectuer chacune de ces opérations directement dans les gestionnaires de route. Mais la même logique serait alors répétée à plusieurs endroits.

Express permet plutôt de placer ces traitements dans des **middlewares**, c'est-à-dire des étapes intermédiaires exécutées pendant le traitement d'une requête.

<Highlight>Un middleware intercepte une requête, effectue une responsabilité précise, puis décide si le traitement doit continuer.</Highlight>

## 1. Le middleware dans Express : 

Un middleware Express est une fonction qui reçoit généralement trois paramètres `(req, res, next)` : 

```js
function journalisation(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next();
}
```

On peut ensuite le monter dans l'application :

```js
app.use(journalisation);
```

Les trois paramètres ont des rôles distincts :

- `req` représente la **requête**;
- `res` représente la **réponse** qui sera envoyée au client;
- `next` permet de transférer le traitement à l'étape suivante.

La requête peut ainsi traverser plusieurs middlewares avant d'atteindre le gestionnaire de route.

### Les trois issues d'un middleware

À chaque exécution, un middleware doit éventuellement mener à l'une de ces trois issues :

1. appeler `next()` pour continuer vers l'étape suivante;
2. produire une réponse avec `res.send()`, `res.json()`, `res.end()`, etc.;
3. transmettre une erreur avec `next(err)`.

Par exemple :

```js
function verifierCle(req, res, next) {
  if (!req.headers["x-api-key"]) {
    return res.status(401).json({
      erreur: "clé manquante",
    });
  }

  next();
}
```

Si la clé est absente, le middleware produit lui-même la réponse.

Sinon, `next()` laisse la requête poursuivre son chemin.

<MarginNote type="erreur" titre="Le piège du next oublié">
Si un middleware ne répond pas et n'appelle pas `next()`, aucune étape suivante ne sera exécutée. La requête reste alors en attente.
</MarginNote>

### Où monter un middleware ?

Un middleware peut être appliqué à plusieurs niveaux.

#### Pour toutes les requêtes :

```js
app.use(journalisation);
```

#### Pour un groupe de routes :

```js
app.use("/admin", authentifier);
```

#### Pour une seule route :

```js
app.get("/profil", authentifier, afficherProfil);
```

Les fonctions fournies par Express peuvent elles aussi être des middlewares.

**Par exemple :**

```js
app.use(express.json());
```

`express.json()` lit un éventuel corps JSON et rend son contenu disponible dans `req.body`.

## 2. L'ordre forme la chaîne de traitement

<Highlight>Dans Express, l'ordre de déclaration détermine l'ordre d'exécution.</Highlight>

Considérons cette route :

```js
app.get(
  "/boites/:id",
  journalisation,
  verifierId,
  chargerBoite,
  afficherBoite
);
```

Pour une requête correspondante, Express essaie les étapes de gauche à droite :

```txt
journalisation
      ↓
verifierId
      ↓
chargerBoite
      ↓
afficherBoite
```

Chaque middleware appelle `next()` lorsqu'il souhaite poursuivre.

Un middleware peut cependant décider de **terminer la chaîne** en produisant une réponse.

Par exemple :

```js
function verifierId(req, res, next) {
  if (!idValide(req.params.id)) {
    return res.status(400).json({
      erreur: "identifiant invalide",
    });
  }

  next();
}
```

Si l'identifiant est invalide, `chargerBoite` et `afficherBoite` ne seront jamais exécutés.

## 3. Les erreurs suivent une autre voie

Un middleware peut rencontrer une erreur qu'il ne souhaite pas transformer directement en réponse.

Il peut alors appeler :

```js
next(err);
```

Express cherche ensuite un **middleware de gestion d'erreurs**.

Celui-ci se distingue par quatre paramètres :

```js
app.use((err, req, res, next) => {
  console.error(err);

  res.status(err.status ?? 500).json({
    erreur: err.message,
  });
});
```

Ce middleware est généralement déclaré après les routes et les autres middlewares.

<MarginNote type="attention" titre="Quatre paramètres">
Express reconnaît un middleware de gestion d'erreurs grâce à sa signature `(err, req, res, next)`. Il faut donc conserver les quatre paramètres, même si `next` n'est pas utilisé directement.
</MarginNote>

### Les fonctions asynchrones avec Express 5

Avec Express 5, une erreur levée dans un middleware `async` ou une promesse rejetée est automatiquement transmise au traitement des erreurs.

Par exemple :

```js
app.get("/boites/:id", async (req, res) => {
  const boite = await Boite.findById(req.params.id);

  res.json(boite);
});
```

Si `findById()` échoue en levant une erreur, Express peut transmettre cette erreur au middleware de gestion d'erreurs.

<MarginNote type="plusloin">
Dans Express 4, les erreurs provenant de nombreuses fonctions `async` devaient généralement être capturées avec `try/catch` puis transmises manuellement avec `next(err)`. Ce motif apparaît donc encore fréquemment dans les exemples plus anciens.
</MarginNote>

## 4. Une chaîne d'étapes indépendantes

Le fonctionnement des middlewares peut être compris comme un **pipeline de traitement**.

Chaque étape :

1. reçoit la requête et la réponse;
2. accomplit une responsabilité particulière;
3. décide ensuite de poursuivre, de répondre ou de signaler une erreur.

Cette organisation rappelle le patron architectural **pipe-et-filtre**.

<MarginNote type="definition" titre="Pipe-et-filtre">
Dans le patron pipe-et-filtre, un traitement est décomposé en plusieurs étapes indépendantes. Chaque filtre accomplit une transformation ou une vérification avant de transmettre le traitement à l'étape suivante.
</MarginNote>

Express n'implémente pas nécessairement une forme pure de ce patron : les middlewares partagent notamment les mêmes objets `req` et `res` et peuvent interrompre la chaîne.

<Highlight>Une bonne chaîne de middlewares est composée de petites étapes ayant chacune une responsabilité claire.</Highlight>

Cela permet de :

- réutiliser une même étape sur plusieurs routes;
- insérer ou retirer une vérification;
- modifier l'ordre des traitements;
- garder les gestionnaires de route centrés sur leur responsabilité principale.

## 5. Authentification et autorisation

L'authentification et l'autorisation illustrent particulièrement bien cette séparation des responsabilités.

**Authentifier** consiste à établir l'identité de l'utilisateur.

**Autoriser** consiste ensuite à déterminer si cet utilisateur possède les droits nécessaires.

Ce sont deux responsabilités différentes.

On peut donc créer deux middlewares :

```txt
authentifier
     ↓
exigerRole("admin")
     ↓
gestionnaire
```

### 5.1 Décrire ce que garantit un middleware

Pour comprendre l'ordre nécessaire, on peut décrire simplement ce que chaque middleware reçoit et ce qu'il garantit.

#### `authentifier`

Il recherche une preuve d'identité dans la requête.

S'il appelle `next()`, il garantit que :

```js
req.utilisateur
```

est défini.

Sinon, il répond `401 Unauthorized`.

#### `exigerRole(role)`

Il suppose que :

```js
req.utilisateur
```

a déjà été défini.

Il vérifie ensuite si l'utilisateur possède le rôle demandé.

S'il possède ce rôle, le traitement continue.

Sinon, le middleware répond `403 Forbidden`.

<Highlight couleur="ambre">L'autorisation dépend du résultat de l'authentification. Leur ordre dans la chaîne n'est donc pas interchangeable.</Highlight>

Un middleware n'est pas limité à l'authentification.

Il peut également préparer des informations dont plusieurs routes auront besoin.

Supposons une API contenant des boites :

  next();
}

## 7. Valider le corps d'une requête

La validation constitue un autre bon candidat pour un middleware.

Avant de créer une boite, on souhaite par exemple vérifier :

```json
{
  "nom": "Archives",
  "capacite": 40
}
```

Les règles peuvent varier selon les ressources, mais le mécanisme reste similaire.

On peut donc créer une **fabrique de middleware**.

<MarginNote type="definition" titre="Fabrique de middleware">
Une fabrique de middleware est une fonction qui retourne un middleware configuré.

`exigerRole("admin")` en est déjà un exemple : `"admin"` configure le middleware qui sera ensuite exécuté par Express.
</MarginNote>

```js
export function validerCorps(regles) {
  return (req, res, next) => {
    const corps = req.body ?? {};
    const erreurs = [];

    for (const [champ, verifier] of Object.entries(regles)) {
      const message =
        verifier(corps[champ]);

      if (message) {
        erreurs.push({
          champ,
          message,
        });
      }
    }

    if (erreurs.length > 0) {
      return res.status(400).json({
        erreurs,
      });
    }

    next();
  };
}
```

Les règles d'une boite peuvent alors être définies séparément :

```js
const reglesBoite = {
  nom: (valeur) =>
    typeof valeur === "string" &&
    valeur.trim() !== ""
      ? null
      : "nom requis",

  capacite: (valeur) =>
    Number.isInteger(valeur) &&
    valeur > 0
      ? null
      : "entier positif attendu",
};
```

Puis appliquées à la route :

```js
app.post(
  "/boites",
  validerCorps(reglesBoite),
  creerBoite
);
```

Le gestionnaire `creerBoite` ne doit plus lui-même répéter toutes les vérifications.

<MarginNote type="attention" titre="Un corps absent">
`req.body` peut être `undefined`, notamment lorsqu'aucun corps n'a été lu. L'expression `req.body ?? {}` garantit donc que la validation travaille au minimum avec un objet vide.
</MarginNote>

<MarginNote type="plusloin">
Dans une véritable application, on utilise souvent une bibliothèque de validation comme Zod ou express-validator. Le principe reste semblable : définir les règles une fois et appliquer la validation avant le gestionnaire de route.
</MarginNote>

## 8. Observer la fin d'une réponse

Les middlewares vus jusqu'ici prennent principalement des décisions **avant** que le gestionnaire produise sa réponse.

Un middleware peut toutefois enregistrer une action qui sera déclenchée plus tard dans le cycle de la réponse.

On peut par exemple mesurer le temps nécessaire au traitement complet d'une requête.

```js
// intergiciels/mesure.js

export function mesurerDuree(req, res, next) {
  const debut = performance.now();

  res.on("finish", () => {
    const duree =
      (performance.now() - debut).toFixed(1);

    console.log(
      `${req.method} ${req.originalUrl} ` +
      `${res.statusCode} ${duree} ms`
    );
  });

  next();
}
```

Puis :

```js
app.use(mesurerDuree);
```

Le middleware :

1. note l'heure de départ;
2. enregistre une fonction qui sera appelée lorsque la réponse sera terminée;
3. appelle immédiatement `next()` pour poursuivre le traitement.

<Highlight>
La réponse ne retraverse pas les middlewares en sens inverse. Ici, le middleware enregistre plutôt un observateur qui sera déclenché lorsque la réponse sera terminée.
</Highlight>

### Pourquoi ne pas simplement écrire du code après `next()` ?

On pourrait être tenté d'écrire :

```js
function mesurerDuree(req, res, next) {
  const debut = performance.now();

  next();

  console.log(
    performance.now() - debut
  );
}
```

Mais `next()` transmet le contrôle à l'étape suivante. Cela ne signifie pas nécessairement que toutes les opérations asynchrones et l'envoi de la réponse sont terminés au moment où le code suivant s'exécute.

L'événement `finish` constitue donc un meilleur point d'observation de la fin de la réponse.

<Checkpoint question="Que se passe-t-il si mesurerDuree est placé après authentifier ?">
Les requêtes interrompues par `authentifier`, par exemple avec un `401`, n'atteignent jamais `mesurerDuree`. Aucun observateur `finish` n'est alors enregistré pour ces requêtes. Si l'objectif est de mesurer toutes les requêtes, `mesurerDuree` doit être placé suffisamment tôt dans la chaîne.
</Checkpoint>

## 9. Un principe que l'on retrouve ailleurs

La chaîne de middlewares Express illustre un principe plus général :

> placer des traitements transversaux entre l'entrée d'une requête et la logique principale de l'application.

On retrouve des idées semblables dans d'autres architectures.

### Passerelle d'API

Dans une architecture composée de plusieurs services, une **passerelle d'API** peut être placée devant ceux-ci.

Elle peut notamment prendre en charge :

- l'authentification;
- la limitation du nombre de requêtes;
- le routage;
- la journalisation.

```txt
client
  ↓
passerelle d'API
  ↓
service
```

### Side-car et maillage de services

Certaines architectures ajoutent également un proxy près de chaque service afin de prendre en charge des responsabilités comme :

- le chiffrement des communications;
- l'observabilité;
- certaines stratégies de reprise;
- le contrôle du trafic.

Le niveau architectural est très différent de celui d'Express, mais l'intention générale se ressemble : **retirer certaines responsabilités transversales de la logique métier principale**.

<Highlight couleur="ambre">
Le middleware Express est donc un exemple concret d'une idée plus générale : décomposer le traitement en responsabilités composables plutôt que concentrer toute la logique dans chaque route.
</Highlight> */}

## À retenir

Un middleware Express est une étape intermédiaire du traitement d'une requête.

Il peut notamment :

- observer ou modifier `req` et `res`;
- appeler `next()` pour poursuivre;
- produire directement une réponse;
- transmettre une erreur;
- préparer des informations pour les étapes suivantes.

L'ordre dans lequel les middlewares sont montés détermine leur ordre d'exécution.
