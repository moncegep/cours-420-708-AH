## Mise en situation

**Ogodo** est un restaurant de quartier de six tables. Jusqu'ici, le service se coordonne sur papier : les serveurs notent les commandes sur un carnet, la cuisine les reçoit sur des billets, et l'addition se calcule à la main. Les erreurs sont fréquentes : une commande modifiée par la mauvaise personne, un plat servi avant d'être prêt, une table libérée alors qu'elle n'a pas encore payé.

Ogodo souhaite remplacer ce fonctionnement par une **API** (interface de programmation applicative : un ensemble de points d'accès par lesquels des applications échangent des données) que les tablettes des serveurs et l'écran de la cuisine pourront interroger.

Tu développes cette API. Elle doit gérer les tables, le personnel, le menu et surtout les commandes, en faisant respecter les règles du service.

## Le service en action

L'animation ci-dessous montre le comportement attendu de ton API. Chaque déplacement du personnel est un geste physique ; chaque pastille qui voyage vers l'API est une **requête HTTP**, et la pastille qui revient est la **réponse**, avec son code de statut.

<ServiceSalle client:visible />

En observant les scénarios, porte attention aux points suivants :

1. **Qui envoie la requête.** Un serveur ou la cuisine. L'en-tête `X-Staff-Id` (visible dans le journal) indique à l'API qui fait la demande.
2. **Quand les données changent.** Une table ou une commande ne change d'état qu'après une réponse de la famille 2xx. Un refus laisse les données intactes.
3. **Ce qui distingue les refus.** Une requête mal formée (400), une action interdite pour cette personne (403) et une action incompatible avec l'état actuel (409) sont trois situations différentes.
4. **Ce que contient le journal.** Chaque ligne du journal pourrait devenir un test de ton API : une requête précise, une réponse attendue.

## Architecture attendue

### Un service, plusieurs modules

L'API reste un seul service, mais elle est organisée en **modules**, un par domaine : `staff` (personnel), `tables`, `menu` et `orders` (commandes). Chaque module regroupe tout ce qui concerne son domaine.

À l'intérieur d'un module, le code est réparti en quatre **couches**, chacune avec une seule responsabilité :

| Couche | Fichier | Responsabilité |
|---|---|---|
| Routes | `*.routes.js` | Associer verbes et chemins aux fonctions du contrôleur. |
| Contrôleur | `*.controller.js` | Lire la requête (paramètres, corps, en-têtes), appeler le service, formuler la réponse HTTP. |
| Service | `*.service.js` | Appliquer les règles métier : validation, droits, transitions, calculs. Ne connaît rien de HTTP. |
| Dépôt | `*.repository.js` | Lire et écrire les données. C'est la seule couche qui sait *où* elles sont stockées. |

Un **dépôt** (en anglais *repository*) est ici un objet qui offre des fonctions comme `findById`, `findAll`, `create`, `update`, et qui cache la manière dont les données sont réellement conservées.

### Les règles de frontière

Ces règles sont au cœur de l'évaluation de l'architecture.

1. Un module n'accède **jamais** au dépôt d'un autre module. Si le service des commandes a besoin d'une table, il passe par le **service** des tables.
2. Les services ne manipulent ni `req` ni `res`. Ils reçoivent des valeurs et retournent des valeurs, ou lèvent une erreur.
3. Les fonctions des dépôts sont **asynchrones** (elles retournent des promesses), même en mémoire. Remplacer plus tard la mémoire par une base de données ne demandera alors aucune modification des services.

<Aside type="tip" title="Pourquoi cette découpe ?">
Dans un cours à venir, ces modules pourraient devenir des services séparés : un service de salle (tables et personnel), un service de menu et un service de commandes. Si les frontières sont respectées dès maintenant, cette séparation consiste surtout à remplacer des appels de fonctions entre modules par des appels HTTP entre services. Si elles ne le sont pas, il faut souvent tout réorganiser.
</Aside>

### Séparer `app.js` et `server.js`

`app.js` exporte une fonction `createApp()` qui construit l'application (middlewares, routes, gestion des erreurs) **sans** appeler `listen`. `server.js` l'importe et démarre l'écoute. Cette séparation permet aux tests de créer une application neuve pour chaque test, sans port réseau.

`createApp()` accepte en option les dépôts à utiliser. C'est une forme d'**injection de dépendances** : plutôt que de créer elle-même ses dépôts, l'application reçoit ceux qu'on lui fournit. Les tests peuvent ainsi partir de données fraîches à chaque fois.

```js
// src/app.js (extrait)
export function createApp({ repositories = createMemoryRepositories() } = {}) {
  const app = express();
  app.use(express.json());
  // ... construire les services à partir des dépôts, puis monter les routes
  app.use(errorHandler);
  return app;
}
```

<Aside type="note" title="Express 5 et les erreurs asynchrones">
Avec Express 5, une erreur levée dans un gestionnaire `async` est dans bien des cas transmise automatiquement au middleware d'erreurs. Avec Express 4, il fallait souvent l'attraper soi-même et appeler `next(err)`. Tu peux donc laisser tes services lever des `HttpError` et les laisser remonter.
</Aside>

## Modèle de données

Les noms de champs sont imposés : ils font partie du contrat.

**StaffMember** (membre du personnel)

| Champ | Type | Remarque |
|---|---|---|
| `id` | entier | généré par l'API |
| `name` | chaîne | non vide |
| `role` | `"server"` ou `"kitchen"` | serveur ou cuisine |

**Table**

| Champ | Type | Remarque |
|---|---|---|
| `id` | entier | généré par l'API |
| `number` | entier | numéro affiché, unique |
| `seats` | entier | nombre de places, de 1 à 12 |
| `status` | `"free"` ou `"occupied"` | libre ou occupée |
| `serverId` | entier ou `null` | serveur assigné quand la table est occupée |
| `guests` | entier | nombre de clients installés, 0 si libre |

**MenuItem** (item du menu)

| Champ | Type | Remarque |
|---|---|---|
| `id` | entier | généré par l'API |
| `name` | chaîne | non vide |
| `category` | `"starter"`, `"main"`, `"dessert"` ou `"drink"` | |
| `priceCents` | entier | prix en cents, strictement positif |
| `available` | booléen | `false` si l'item ne peut pas être commandé |

**Order** (commande)

| Champ | Type | Remarque |
|---|---|---|
| `id` | entier | généré par l'API |
| `tableId` | entier | |
| `serverId` | entier | serveur assigné à la table au moment de la commande |
| `status` | voir le cycle de vie | |
| `items` | tableau | lignes de la commande (voir ci-dessous) |
| `history` | tableau | historique des changements de statut |
| `createdAt` | chaîne ISO 8601 | |

Une ligne de commande contient `menuItemId`, `name`, `quantity`, `unitPriceCents` et, au besoin, `note`. Une entrée d'historique contient `status`, `at` (date et heure) et `byStaffId`.

<Aside type="tip" title="Pourquoi des cents ?">
Les nombres à virgule de JavaScript ne représentent pas exactement certains montants (essaie `0.1 + 0.2` dans la console). Stocker les prix en **cents entiers** évite ces erreurs d'arrondi. Le format **ISO 8601** est une norme d'écriture des dates, par exemple `2026-10-15T18:02:00Z` ; `new Date().toISOString()` la produit directement.
</Aside>

## Identifier le personnel

Les actions du service (installer des clients, commander, changer un statut, libérer une table) exigent de savoir **qui** fait la demande. Au TP1, cette identification se fait par un en-tête HTTP :

```
X-Staff-Id: 1
```

Un middleware partagé lit cet en-tête et retrouve le membre du personnel correspondant. Si l'en-tête est absent, n'est pas un entier, ou ne correspond à aucun membre, l'API répond **401**.

<Aside type="caution" title="Ce n'est pas de l'authentification">
N'importe qui peut écrire `X-Staff-Id: 1` dans une requête. Cet en-tête sert à **identifier** l'auteur d'une action, pas à **prouver** son identité. L'authentification véritable (jetons, mots de passe) sera abordée plus tard. Les routes de gestion (personnel, tables, menu) n'exigent pas cet en-tête au TP1.
</Aside>

## Cycle de vie d'une commande

Une commande passe par une suite d'états. Seules les transitions du tableau sont permises.

| De | Vers | Qui peut la demander |
|---|---|---|
| `placed` (prise) | `in_kitchen` (en cuisine) | le serveur assigné |
| `placed` (prise) | `cancelled` (annulée) | le serveur assigné |
| `in_kitchen` (en cuisine) | `ready` (prête) | un membre de la cuisine |
| `ready` (prête) | `served` (servie) | le serveur assigné |
| `served` (servie) | `paid` (payée) | le serveur assigné |

`paid` et `cancelled` sont des **états finaux** : aucune transition n'en part. Une commande est dite **active** tant qu'elle n'est pas dans un état final.

Toute transition absente du tableau répond **409**, avec le statut actuel et les statuts permis :

```json
{
  "error": {
    "code": "INVALID_TRANSITION",
    "message": "Impossible de passer de in_kitchen à served.",
    "details": { "currentStatus": "in_kitchen", "allowed": ["ready"] }
  }
}
```

Chaque création et chaque transition réussie ajoute une entrée à `history`. L'historique n'est jamais modifié ni effacé : il garde la trace de *qui* a fait *quoi* et *quand*.

## Règles métier

**Tables**

1. Le numéro (`number`) d'une table est unique : un doublon répond 409.
2. Installer des clients exige un membre de rôle `server` (sinon 403), une table libre (sinon 409) et un nombre de clients entier entre 1 et le nombre de places (sinon 400).
3. Seul le serveur assigné peut libérer une table (sinon 403). Une table qui a encore une commande active ne peut pas être libérée (409).
4. Une table occupée ne peut pas être supprimée (409).

**Commandes**

5. Seul le serveur assigné à la table peut y créer une commande (sinon 403). La table doit être occupée (sinon 409).
6. Une commande contient de 1 à 20 lignes. Chaque ligne référence un item existant et disponible, avec une quantité entière de 1 à 20 et une note facultative d'au plus 200 caractères.
7. Le nom et le prix de l'item sont **copiés** dans la ligne au moment de la commande. Un changement de prix au menu ne modifie pas une commande existante.
8. Les lignes d'une commande ne peuvent être remplacées que par le serveur assigné (sinon 403), et seulement au statut `placed` (sinon 409).
9. Une table peut avoir plusieurs commandes (par exemple une seconde commande pour les desserts).

### Ordre des vérifications

Quand plusieurs problèmes sont présents, l'API signale le premier dans cet ordre : identification (401), existence de la ressource (404), validité des données (400), droit d'agir (403), compatibilité avec l'état actuel (409). Pour une transition, le droit d'agir dépend du statut demandé : demander `ready` exige un membre de la cuisine, tout autre statut exige le serveur assigné.

Par exemple, si Léa demande `served` pour sa commande encore `in_kitchen`, elle a le droit d'agir mais la transition est invalide : 409. Si Marc demande `served`, il n'a pas le droit d'agir : 403.

## Erreurs

Toutes les erreurs suivent le même format. `details` est facultatif.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "La commande est invalide.",
    "details": [
      { "field": "items[0].menuItemId", "message": "L'item 99 n'existe pas au menu." },
      { "field": "items[1].quantity", "message": "La quantité doit être un entier entre 1 et 20." }
    ]
  }
}
```

| Code HTTP | `error.code` | Situation |
|---|---|---|
| 400 | `VALIDATION_ERROR` | données invalides ; `details` liste **toutes** les erreurs trouvées |
| 401 | `UNAUTHENTICATED` | `X-Staff-Id` absent ou inconnu |
| 403 | `FORBIDDEN` | la personne identifiée n'a pas le droit de faire cette action |
| 404 | `NOT_FOUND` | la ressource n'existe pas |
| 409 | `CONFLICT` ou `INVALID_TRANSITION` | la demande est incompatible avec l'état actuel |
| 500 | `INTERNAL_ERROR` | erreur imprévue ; le message ne révèle aucun détail interne |

Les services lèvent des instances d'une classe `HttpError` (avec un statut, un code et un message). Un **middleware d'erreurs centralisé** les convertit en réponse JSON. Aucun contrôleur ne construit lui-même une réponse d'erreur.

## Addition et taxes

`GET /orders/:id/bill` calcule l'addition d'une commande servie ou payée (sinon 409) :

- `subtotalCents` : somme de `quantity × unitPriceCents` sur toutes les lignes ;
- `tpsCents` : 5 % du sous-total ;
- `tvqCents` : 9,975 % du sous-total ;
- `totalCents` : sous-total + TPS + TVQ.

Chaque taxe est arrondie au cent le plus proche (`Math.round`). Exemple, pour deux tourtières et une poutine :

```json
{ "orderId": 12, "subtotalCents": 6000, "tpsCents": 300, "tvqCents": 599, "totalCents": 6899 }
```

La TVQ vaut ici 598,5 cents, arrondis à 599. Ce cas d'arrondi mérite un test.

## Tests attendus

Les tests s'exécutent avec `npm test` (script `vitest run`). Chaque test part de données fraîches : construis une nouvelle application ou de nouveaux dépôts dans un `beforeEach`.

**Tests des services** (tests unitaires : on appelle directement les fonctions du service, sans HTTP)

1. Chaque transition permise du cycle de vie.
2. Au moins trois transitions interdites, qui lèvent une erreur 409.
3. Les refus de droit : un autre serveur, et la cuisine qui tente une transition réservée au serveur.
4. La validation d'une commande, dont au moins un cas avec plusieurs erreurs simultanées.
5. Le calcul de l'addition, incluant le cas d'arrondi ci-dessus.
6. Le refus de libérer une table qui a une commande active.

**Tests des points d'accès** (avec supertest : on envoie de vraies requêtes HTTP à l'application)

7. Au moins un test pour chaque code utilisé : 200, 201, 204, 400, 401, 403, 404 et 409, en vérifiant aussi le format du corps d'erreur.
8. Un scénario complet, comme dans l'animation : installer, commander, envoyer en cuisine, marquer prête, servir, calculer l'addition, payer, libérer.

```js
// tests/endpoints/orders.test.js (extrait)
import request from 'supertest';
import { beforeEach, describe, expect, it } from 'vitest';
import { createApp } from '../../src/app.js';

describe('PATCH /orders/:id/status', () => {
  let app;
  beforeEach(() => {
    app = createApp();
  });

  it('refuse de servir une commande encore en cuisine (409)', async () => {
    // ... installer la table 4 et créer une commande envoyée en cuisine
    const res = await request(app)
      .patch('/orders/1/status')
      .set('X-Staff-Id', '1')
      .send({ status: 'served' });

    expect(res.status).toBe(409);
    expect(res.body.error.code).toBe('INVALID_TRANSITION');
  });
});
```

## Bonus : PostgreSQL avec Supabase

Remplace la persistance en mémoire par une base PostgreSQL hébergée sur **Supabase** (une plateforme qui fournit une base PostgreSQL en ligne).

- Écris le schéma SQL dans `db/schema.sql` (tables du personnel, des tables du restaurant, du menu, des commandes, des lignes de commande et de l'historique).
- Écris de nouveaux dépôts (par exemple `orders.repository.postgres.js`) qui offrent **exactement les mêmes fonctions** que les dépôts en mémoire. Tu peux utiliser `@supabase/supabase-js` ou `pg`.
- Choisis le stockage par une variable d'environnement, par exemple `STORAGE=memory` ou `STORAGE=postgres`.
- Les informations de connexion restent dans `.env`, jamais dans Git. Fournis plutôt un `.env.example` sans secret.
- Les tests continuent de s'exécuter sur les dépôts en mémoire.

Le critère principal du bonus : **aucun service n'est modifié** pour passer d'un stockage à l'autre. C'est la démonstration que les frontières de ton architecture tiennent.
